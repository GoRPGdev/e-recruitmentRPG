Prinsip yang menjaga “fleksibel” tidak jadi “berantakan”

Ini aturan main yang harus dipegang berdua. Kalau dilanggar, yang pertama mati adalah modul Report — dan biasanya baru ketahuan setelah data sudah banyak.

Boleh diubah HR lewat UIWajib tetap di kode / skema
Daftar & urutan tahap dalam satu flowDaftar status_global — 9 nilai, terkunci
Tahap wajib atau opsionaltipe_tahap — 7 nilai tetap
SLA & PIC per tahapStruktur entitas inti
Batas upaya kontak per flowAturan dedupe kandidat
Isi dropdown alasan + efek statusnyaTransaksi, penguncian baris, audit trail
Daftar posisi, departemen, outlet, dokumenHak akses
  1. Soft delete wajib, hard delete haram.Kalau HR menghapus remark “Ekspektasi gaji tidak sesuai”, empat puluh lamaran lama yang memakainya jadi yatim dan history-nya rusak. Semua master pakai is_aktif = 0: baris lama tetap terbaca, dropdown baru tidak menampilkannya.
  2. Flow di-snapshot per lamaran.Saat lamaran dibuat, seluruh APPLICATION_STAGES di-generate dari template. Perubahan template sesudahnya tidak menyentuh lamaran yang sedang berjalan. Tanpa ini, HR menambah satu tahap dan dua ratus lamaran aktif berubah alurnya diam-diam.
  3. Tahap beda per orang lewat penanda sisipan.HR boleh menyisipkan tahap ad-hoc ke satu lamaran tanpa mengubah template. Saat menyisip, urutan seluruh baris lamaran itu di-renumber dalam satu transaksi.
  4. Jangan bikin field dinamis.Godaan berikutnya adalah “field per tahap juga bisa ditambah HR”. Jangan. SQL Server 2008 R2 tidak punya tipe JSON, jadi ujungnya kolom teks yang tidak bisa di-query. Yang fleksibel cukup struktur alur dan daftar pilihan; yang mau dihitung harus kolom bertipe jelas.

Kalau tiap flow beda tahapnya, funnel-nya bagaimana?

Ini pertanyaan yang paling menentukan. HQ Manager punya sepuluh tahap, MP Outlet cuma dua — jadi funnel tidak bisa dihitung dari nama tahap. Jawabannya: setiap tahap punya dua identitas.

▸
Satu syarat untuk HR. Setiap tahap baru yang dibuat sendiri wajib memilih tipe tahap dari tujuh nilai tetap itu. Itu satu-satunya harga yang dibayar supaya tahap buatan sendiri tetap masuk hitungan report.

Perubahan skema yang dibutuhkan

Semua ditulis sebagai migrasi baru, bukan mengedit file yang sudah ada. Yang paling berdampak adalah formulir pelamar — dua puluh satu field dari Google Forms tidak muat di tabel kandidat yang sekarang.

Formulir pelamar — pisahkan tiga jenis data

Kuncinya memisahkan data yang melekat ke orang dari yang melekat ke lamaran. Orang yang sama bisa melamar dua kali dengan gaji harapan yang berbeda. Email dijadikan field wajib — kolomnya sudah ada di ERD, jadi tidak perlu diubah.

-- Email: kolom CANDIDATES.email SUDAH ADA di ERD v1.2.
-- Cukup jadikan field WAJIB di form. Dedupe: no_wa_normal -> email -> hash CV.

-- Data milik ORANG (jarang berubah antar lamaran)
ALTER TABLE CANDIDATES ADD
  tempat_lahir         VARCHAR(100)  NULL,
  jenis_kelamin        CHAR(1)       NULL,   -- 'L' / 'P' — disimpan, TIDAK jadi filter
  nama_sekolah         VARCHAR(150)  NULL,

  alamat_lengkap       VARCHAR(500)  NULL,
  status_pernikahan    VARCHAR(20)   NULL,
  kontak_darurat_nama  VARCHAR(150)  NULL,
  kontak_darurat_telp  VARCHAR(30)   NULL,
  kontak_darurat_hub   VARCHAR(30)   NULL;

-- Data milik LAMARAN (beda tiap kali orang yang sama melamar lagi)
CREATE TABLE APPLICATION_PROFILE (
  id_lamaran           INT           NOT NULL PRIMARY KEY,
  perusahaan_terakhir  VARCHAR(150)  NULL,
  jabatan_terakhir     VARCHAR(150)  NULL,
  periode_kerja        VARCHAR(100)  NULL,
  gaji_terakhir        DECIMAL(18,2) NULL,   -- akses: HR Admin ke atas
  gaji_diharapkan      DECIMAL(18,2) NULL,   -- akses: HR Admin ke atas
  diisi_pada           DATETIME      NULL
);

-- Data kesehatan = data pribadi SPESIFIK (UU PDP 27/2022 Pasal 4 ayat 2). HR pakai.
-- Consent TERPISAH. Akses HR Spv saja, tiap buka dicatat di ACCESS_LOG_SENSITIF.
CREATE TABLE CANDIDATE_HEALTH (
  id_kandidat          INT           NOT NULL PRIMARY KEY,
  riwayat_penyakit     VARCHAR(500)  NULL,
  consent_khusus       BIT           NOT NULL DEFAULT 0,
  consent_pada         DATETIME      NULL
);

Keputusan HR

Dijawab Mas Fachri, 3 September 2026. Kelima jawaban ini sudah diserap ke skema di atas — tidak ada lagi yang menggantung sebelum migrasi ditulis.

1
Tambah kolom Email. selesai

Field Email jadi wajib di form publik. Kolom CANDIDATES.email sudah ada di ERD, tidak perlu ALTER. Dedupe berjalan penuh: nomor WA, lalu email, lalu hash CV.

2
Data kesehatan: butuh, disimpan. selesai

Tabel CANDIDATE_HEALTH dengan centang persetujuan terpisah dari consent umum. Akses paling ketat — HR Spv saja — dan setiap kali dibuka dicatat di ACCESS_LOG_SENSITIF.

3
Gaji terakhir & harapan: Admin HR. selesai

Permission LIHAT_GAJI_PELAMAR untuk HR Admin ke atas. Berbeda dari akses nomor rekening (HR Spv saja) dan dari range gaji / offer (HR Spv + BOD).

4
Gender & status pernikahan: seperti usul. selesai

Disimpan sebagai data. Tidak jadi opsi filter di dashboard. Tidak pernah tampil di posting maupun form publik.

5
Satu posisi, satu link — masuk otomatis ke pipeline posisi itu. selesai

Betul. Tiap requisition yang di-posting punya url_slug sendiri, jadi beda posisi beda link. Slug sudah menunjuk ke posisinya, jadi kandidat tidak memilih posisi — cukup ditampilkan “Anda melamar untuk: …”. Saat submit, lamaran dibuat dengan requisition & flow dari slug itu, lalu tahapannya di-generate, dan kandidat langsung muncul di pipeline posisi tersebut tanpa entri manual. Satu link “umum” tetap ada untuk walk-in / talent pool — di situ dropdown posisi muncul, diisi dari MPR yang sedang Sourcing. MPR yang sudah terpenuhi / ditutup otomatis form_aktif = 0.

CLAUDE.md untuk repo — salin apa adanya

# E-Recruitment Ratu Pertiwi Group

## Stack (terkunci)
CodeIgniter 3 · PHP 7.4 · SQL Server 2008 R2 · Database-First (logika transaksi di Stored Procedure)

## Batasan T-SQL SQL Server 2008 R2 — JANGAN dipakai
| Tidak ada          | Pakai ini                          |
|--------------------|------------------------------------|
| OFFSET FETCH NEXT  | ROW_NUMBER() OVER (...) di CTE     |
| THROW              | RAISERROR(@msg, 16, 1)             |
| TRY_CONVERT/CAST   | ISDATE() / ISNUMERIC() + CASE      |
| CONCAT() / IIF()   | + dengan ISNULL(), CASE WHEN       |
| tipe & fungsi JSON | normalisasi penuh                  |
| SEQUENCE           | IDENTITY                           |
| FORMAT()           | CONVERT() dengan style code        |
| STRING_SPLIT       | tabel bantu atau XML split         |

## Aturan wajib
- Semua query pakai parameter binding. Tidak pernah string concat ke SQL.
- Paginasi selalu pola ROW_NUMBER() — jangan andalkan limit() driver sqlsrv CI3.
- Setiap perubahan status menulis APPLICATION_HISTORY di transaksi yang sama.
- Master data pakai soft delete (is_aktif = 0). Tidak pernah DELETE.
- Flow di-snapshot ke APPLICATION_STAGES saat lamaran dibuat.
- Batas upaya kontak dibaca dari M_FLOW.maks_upaya_kontak, bukan angka tetap di SP.
- File fisik di luar webroot; DB hanya simpan path, hash, metadata.

## Migrasi
File di database/migrations/, format YYYYMMDD_HHMM__nama.sql
File yang sudah di-push TIDAK PERNAH diedit — buat file baru.
Setiap skrip mencatat dirinya ke SCHEMA_MIGRATIONS di akhir eksekusi.

## JANGAN
- Jangan pernah menyentuh database produksi. Dev saja.
- Jangan install ODBC Driver 18 (tidak mendukung SQL Server 2008 R2). Pakai 17.4+.
- Jangan bikin field dinamis / EAV.

Alur Git berdua

Pembagian kerja dilakukan per modul vertikal — satu orang memegang database, stored procedure, controller, dan view untuk satu modul. Kalau dibagi per lapisan (satu orang database, satu orang PHP), yang PHP menunggu terus.

main                    ← selalu jalan
 ├─ feat/master-requisition  Kahfi
 └─ feat/intake-form         Kiki
# sebelum mulai
git pull --rebase origin main

# ... kerja, commit kecil-kecil ...
git commit -m "feat(mpr): form pengajuan"

# sebelum push
git pull --rebase origin main
git push origin feat/master-requisition
  1. Nama file migrasi pakai timestamp, bukan nomor urut.20260903_1430__create_master.sql, bukan V001__…. Kalau dua orang membuat migrasi di hari yang sama, tidak tabrakan nomor.
  2. Migrasi yang sudah di-push tidak pernah diedit.Salah? Buat migrasi koreksi baru. Ini yang menjaga database dev berdua tidak menyimpang diam-diam.
  3. Satu modul satu orang.Jangan dua-duanya menyentuh controller yang sama di minggu yang sama.
  4. File yang sering bentrok diubah di commit kecil sendiri.routes.php, layout, dan CSS langsung di-merge, jangan menumpuk di branch panjang.
